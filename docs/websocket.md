# WebSocket-контракт

Канал: **клиент ↔ Go realtime**. Наружу через Caddy как `wss://<домен>/ws`.
Локально — `ws://localhost:8080/ws`.

Версия документа: **v1**, 13.08.2026.

---

## 1. Общие правила ✅

Действуют для всех кадров, включая будущие. Нарушение — ломающее изменение.

**Формат.** Текстовые кадры WebSocket, каждый — один JSON-объект. Бинарные кадры не
используются. Батчинг делается полем-массивом внутри кадра, а не склейкой кадров.

**Обязательное поле.** У каждого кадра есть `type` — строка вида `группа.действие`
в нижнем регистре. Кадр без `type` невалиден.

**Именование.** `snake_case` для всех полей. Без исключений: `text_id`, а не `textId`
и не `TextID`.

**Неизвестные поля.** Обе стороны игнорируют поля, которых не знают, и **не считают
это ошибкой**. Это то, что позволяет добавлять необязательные поля без смены версии.

**Неизвестные `type`.** Получатель отвечает `error` с кодом `unknown_type` и продолжает
работу. Соединение не рвётся.

**Время.** Все временные метки — целое число **миллисекунд от момента, когда клиент получил
`session.started`**. Не абсолютные метки, не UNIX-время, не время сервера.

> Клиент берёт `performance.now()` в момент получения `session.started` за ноль и дальше
> считает от него. `performance.now()` монотонен и не прыгает при переводе системных часов —
> `Date.now()` для этого не годится.

**Размеры.** Максимальный кадр — **64 КБ**. Больше — `error` с кодом `frame_too_large`,
соединение закрывается.

> ⚠️ Сейчас в `session.go` стоит `SetReadLimit(512)`. Батч из 16 нажатий кириллицей
> в это не помещается — соединение будет рваться молча. Поднять до `65536`.

**Ping/pong.** Сервер шлёт WS-ping раз в **30 секунд**, read deadline — **75 секунд**.
Клиент отвечает pong автоматически (браузер делает это сам). Прикладного `ping`-кадра нет.

> ⚠️ Сейчас: ping раз в 55 с при deadline 60 с. Один потерянный ping — и живое соединение
> закрывается. Запас должен быть кратным интервалу, а не 5 секунд.

**Порядок.** WebSocket гарантирует порядок доставки. Ни у одного кадра нет
номера последовательности, и он не нужен — кроме `session.resume`, см. §3.7.

## 2. Подключение и аутентификация ✅

### 2.1. `auth` — клиент → сервер

**Первый кадр после установки соединения.** Обязателен всегда, даже для анонима.

```json
{ "type": "auth", "v": 1, "token": "eyJhbGciOi...", "anon_id": null }
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `v` | int | да | Версия протокола. Сейчас `1`. |
| `token` | string \| null | да | Access-JWT, выпущенный Python. `null` для анонима. |
| `anon_id` | string \| null | нет | UUID v4 из `localStorage`. Только при `token: null`. |

Токен передаётся кадром, **а не query-параметром**: query оседает в логах Caddy в открытом
виде, и оттуда его можно забрать.

`anon_id` — устойчивый идентификатор браузера без аккаунта. Нужен, чтобы забеги, сделанные до
регистрации, потом можно было привязать к аккаунту (решение по привязке — этап 3, но поле
заводим сразу, иначе привязывать будет нечего).

### 2.2. Поведение сервера

| Ситуация | Результат |
|---|---|
| `token` валиден | Сессия пользовательская, `user_id` из claim'а |
| `token` протух или подпись не сошлась | `error` с кодом `auth_invalid`, **сессия становится анонимной**, соединение живёт |
| `token: null` | Сессия анонимная |
| `v` не поддерживается | `error`, код `protocol_version_unsupported`, `fatal: true`, закрытие |
| Кадра нет 5 секунд | Сессия анонимная, работа продолжается |
| Первый кадр не `auth` | `error`, код `bad_frame`, сессия анонимная, кадр обрабатывается по своему типу |

Анонимная сессия — полноценная: печатать можно, результат сохраняется. Недоступны только
гонки и уроки (нужен `user_id`).

### 2.3. Claim'ы JWT

Вынесены в отдельный файл: **`contracts/jwt.md`**. Там же — refresh-токен, таблица симптомов
при расхождении секретов и кросс-языковой тест для CI.

Здесь достаточно двух фактов: алгоритм **HS256**, секрет общий, и Go **обязан** проверять
`typ == "access"` — иначе refresh-токен на 30 дней пускается в WebSocket как
пятнадцатиминутный access.

## 3. Одиночный забег

Этап 2. Разделы 3.1–3.6 — ✅ **зафиксировано**, 3.7 — 🟡.

### 3.1. `session.start` — клиент → сервер ✅

```json
{ "type": "session.start", "text_id": "8f14e45f-ceea-467a-9f0a-1c3bd0a3f7d2", "mode": "solo" }
```

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `text_id` | string (UUID v4) | да | Получен клиентом из `GET /api/v1/texts/random` |
| `mode` | enum | да | `solo` \| `lesson`. `race` — только через `room.join` |

Клиент передаёт **только идентификатор**, не сам текст. Эталон Go забирает у Python
(`GET /internal/texts/{id}`). Иначе подменённый клиент пришлёт «текст» из трёх букв,
напечатает его за секунду, и вся серверная валидация станет фикцией.

### 3.2. `session.started` — сервер → клиент ✅

```json
{
  "type": "session.started",
  "session_id": "01J9X8K2M4P7Q1R3S5T7V9W2Y4",
  "text_id": "8f14e45f-ceea-467a-9f0a-1c3bd0a3f7d2",
  "text_length": 247,
  "allow_backspace": true,
  "server_time_ms": 1755082800123
}
```

| Поле | Тип | Описание |
|---|---|---|
| `session_id` | string | Идентификатор сессии. Нужен для `session.resume` |
| `text_length` | int | Длина эталона **в графемах**, не в байтах |
| `allow_backspace` | bool | Правило забега, см. §3.4. Приезжает с сервера, а не зашито во фронтенде |
| `server_time_ms` | int | UNIX-мс сервера. Только для диагностики рассинхрона часов |

**Клиент запускает отсчёт `t` от момента получения этого кадра.** Не от нажатия кнопки
«старт», не от `session.start`.

> ⚠️ `session_id` сейчас генерируется как `time.Now().UnixNano()` в виде строки. Два
> подключения в одну наносекунду маловероятны, но идентификатор ещё и предсказуем, а по нему
> восстанавливается сессия (§3.7). Нужен ULID или UUID v4.

### 3.3. `keystroke.batch` — клиент → сервер ✅

Клиент копит нажатия и шлёт их пачкой: **раз в 150 мс или каждые 16 нажатий**, что наступит
раньше. Отдельного кадра на одно нажатие нет.

Честно про выигрыш: при 100 WPM это ~8 нажатий в секунду, то есть в батч попадает
один-два символа, а не двадцать. Смысл здесь не в сжатии, а в том, что **частота кадров
перестаёт зависеть от скорости печати** — она ограничена сверху семью в секунду, кто бы ни
печатал. Это же выравнивает клиентский такт с серверным троттлингом `session.progress`
(тоже 150 мс), так что на тик приходится один обмен, а не случайное чередование. Порог в
16 нажатий — страховка от всплеска: вставка из буфера обмена или залипшая клавиша.

```json
{
  "type": "keystroke.batch",
  "seq": 0,
  "items": [
    { "char": "П", "t": 0 },
    { "char": "р", "t": 143 },
    { "char": "и", "t": 251 },
    { "char": "Backspace", "t": 402 },
    { "char": "и", "t": 498 }
  ]
}
```

| Поле | Тип | Описание |
|---|---|---|
| `seq` | int | Номер батча с нуля. Возрастает на единицу |
| `items[].char` | string | **Ровно один графемный кластер**, либо служебное значение `"Backspace"` |
| `items[].t` | int | Мс от `session.started`. Строго возрастает внутри забега |

Внутри массива `t` возрастает; между соседними батчами — тоже. Пустой `items` игнорируется.

`seq` нужен ровно для одного сценария — `session.resume` (§3.7): после обрыва клиент
досылает буфер, и сервер по `seq` отбрасывает то, что уже принял. В обычном забеге он не
используется: WebSocket и так гарантирует порядок. Батч с `seq`, который уже обработан,
игнорируется молча — это не ошибка, а нормальный ретрай.

**Что сюда не попадает:** модификаторы (Shift, Ctrl, Alt) отдельными событиями, стрелки,
Tab, Escape, Enter вне текста. Клиент отдаёт результат ввода, а не поток событий клавиатуры.
Заглавная «П» приезжает как `"П"`, а не как `Shift` + `"п"`.

### 3.4. Backspace и модель ошибки ✅

> Это ADR-0003 и решение, от которого зависит формула точности. Зафиксировано так:

**Позиция сдвигается на каждом символьном нажатии — верном и ошибочном.** Ошибочный символ
остаётся на своём месте и подсвечивается красным, курсор идёт дальше.

Это не косметика, а условие того, что Backspace вообще имеет смысл: если при ошибке позиция
стоит на месте, стирать нечего, и модель автоматически превращается в «исправляй здесь и
сейчас». Двух моделей одновременно не бывает — выбрана эта.

**Backspace разрешён.** Позиция уменьшается на 1 (не ниже нуля), символ в этой позиции
снова считается ненабранным.

**Ошибка, однажды сделанная, остаётся в счётчике навсегда.** Стирание не «отменяет» ошибку:
иначе точность 100% достигается методом «печатай наугад и стирай», и метрика перестаёт
что-либо значить.

**Сам Backspace не входит в знаменатель точности** — это исправление, а не попытка набрать
символ.

**Забег завершается, когда позиция достигла `text_length`** — независимо от того, сколько
символов на пути оказались ошибочными.

> ⚠️ Сейчас в `ProcessKeystroke` позиция сдвигается **только при верном символе**
> (`if isError { s.Errors++ } else { s.Position++ }`) — то есть реализована противоположная
> модель, а Backspace не обрабатывается вовсе. Это правка на несколько строк, но сделать её
> надо до того, как фронтенд начнёт писать движок под другую логику.

Отсюда формулы, единые для фронтенда и Go (расхождение в цифре на экране и цифре в базе —
худшее, что может случиться с доверием к продукту):

```
correct       = число нажатий, совпавших с ожидаемым символом
typed         = число нажатий, кроме Backspace
accuracy      = correct / typed * 100                      (%)

duration_ms   = t последнего нажатия − t первого нажатия   (не от session.started!)
minutes       = duration_ms / 60000

wpm_raw       = (typed   / 5) / minutes
wpm_net       = (correct / 5) / minutes
```

`duration_ms` считается **от первого нажатия**, а не от старта сессии: иначе пауза «глянул
на текст, собрался» уезжает в знаменатель и занижает WPM у всех.

> ⚠️ Сейчас в `FinishSession()` длительность берётся как `time.Since(s.StartTime)`, то есть
> от `session.start` по серверным часам. Это и включает раздумья, и делает результат
> зависимым от сетевой задержки. Считать надо по `t` из батчей.

> ⚠️ Там же: `wpm` считается по `correct`, а `accuracy` — по `total = len(Keystrokes)`.
> После разрешения Backspace `total` перестанет быть знаменателем точности.

### 3.5. `session.progress` — сервер → клиент ✅

Троттлинг **150 мс**. Отправляется, только если с прошлой отправки что-то изменилось.

```json
{
  "type": "session.progress",
  "t": 12400,
  "position": 42,
  "errors": 3,
  "completed": false
}
```

| Поле | Тип | Описание |
|---|---|---|
| `t` | int | Метка последнего учтённого нажатия. По ней клиент понимает, что именно сверяет |
| `position` | int | Авторитетная позиция в тексте, в графемах |
| `errors` | int | Авторитетное число ошибок за забег |
| `completed` | bool | `position == text_length` |

Отрисовка на клиенте идёт **по локальному движку**, а не по этим кадрам — иначе каретка
будет дёргаться с задержкой сети. Этот кадр нужен для сверки: если `position` расходится
с локальным больше чем на 3, это баг синхронизации, клиент показывает индикатор рассинхрона
и пишет в консоль. Молча подстраиваться под сервер не надо — так баг не найдётся никогда.

При `completed: true` клиент шлёт `session.finish`. Если не прислал за 5 секунд — сервер
завершает забег сам.

> ⚠️ Сейчас `session.progress` шлётся на каждое нажатие, без троттлинга, и содержит лишнее
> поле `length` (оно уже приехало в `session.started`).

### 3.6. Завершение: `session.finish` → `session.result` → `session.saved` ✅

**Клиент → сервер:**

```json
{ "type": "session.finish", "t": 2380 }
```

`t` — метка последнего нажатия по часам клиента. Метрик клиент не присылает: их всё равно
пришлось бы пересчитать, доверять им нельзя. `t` сервер использует только для сверки — если
он расходится с последним принятым нажатием больше чем на 500 мс, значит часть батчей
до сервера не доехала, и забег получает флаг.

**Сервер → клиент, сразу:**

```json
{
  "type": "session.result",
  "session_id": "01J9X8K2M4P7Q1R3S5T7V9W2Y4",
  "wpm_net": 62.4,
  "wpm_raw": 65.1,
  "accuracy": 95.8,
  "duration_ms": 47320,
  "typed": 253,
  "correct": 242,
  "errors": 11
}
```

**Сервер → клиент, после подтверждения от Python:**

```json
{
  "type": "session.saved",
  "session_id": "01J9X8K2M4P7Q1R3S5T7V9W2Y4",
  "run_id": "b2f4c8a1-...",
  "is_personal_best": true,
  "flagged": false
}
```

Два кадра вместо одного — это прямое следствие раздела 4.7 документации («Python недоступен,
Go жив»). Результат показывается мгновенно и не зависит от того, жив ли Python; факт
сохранения приезжает отдельно. Если `session.saved` не пришёл за 10 секунд, фронтенд
показывает «результат сохранится позже» и **не** блокирует интерфейс. Go в это время
докладывает результат из очереди `pending_runs` в Redis.

> ⚠️ Сейчас `session.result` уходит клиенту до вызова `SubmitRun`, а ответ Python
> отбрасывается целиком — `run_id` и `is_personal_best` не доезжают до клиента никогда.
> Поле `is_personal_best` при этом зачем-то отправляется **в** Python со значением `false`.
> Направление у него ровно обратное: считает и возвращает его Python.

### 3.7. `session.resume` — клиент → сервер 🟡

Этап 3. Сервер держит состояние сессии в Redis **30 секунд** после обрыва.

```json
{
  "type": "session.resume",
  "session_id": "01J9X8K2M4P7Q1R3S5T7V9W2Y4",
  "last_t": 12480
}
```

Шлётся сразу после `auth` вместо `session.start`. `last_t` — метка последнего нажатия,
которое клиент считает отправленным; сервер по ней отбрасывает дубли из буфера, который
клиент копил во время обрыва.

Ответ — `session.started` с тем же `session_id` плюс `resumed: true`, `position`, `errors`.
Если сессия не найдена или протухла — `error` с кодом `session_not_found`, клиент начинает
забег заново.

В соло забег продолжается с той же точки. В гонке соперники не ждут (см. §4).

## 4. Гонка ⚪

Этап 4. **Эскиз.** Поля наверняка изменятся — фиксировать перед началом этапа, отдельным PR.
Здесь важна не форма полей, а то, что уже сейчас видно: это тот же код сессии, что и в соло,
плюс рассылка. Ради этого и было принято решение 2.1 «соло — это гонка из одного участника».

**Клиент → сервер:** `room.join` (`code`), `room.ready` (`ready`), `room.leave`,
плюс те же `keystroke.batch` и `session.finish`.

**Сервер → клиент:** `room.state`, `room.countdown`, `race.start`, `race.progress`,
`race.participant_finished`, `room.results`.

```json
{
  "type": "race.progress",
  "t": 12400,
  "participants": [
    { "user_id": 17, "position": 142, "wpm_net": 71.2, "errors": 2, "finished": false },
    { "user_id": 23, "position": 118, "wpm_net": 58.9, "errors": 5, "finished": false }
  ]
}
```

Рассылается **сводкой раз в 150 мс**, а не пересылкой чужих нажатий: при пересылке каждого
нажатия каждому трафик растёт квадратично от числа участников.

Крайние случаи, которые надо описать здесь **до** написания кода — они дороже самого
протокола:

- кто запускает отсчёт: хост или автостарт по готовности всех;
- что происходит при обрыве у участника посреди заезда;
- сколько ждём отставших после финиша первого;
- что если все вышли до финиша;
- можно ли войти в комнату после `race.start` (предлагается: нет, только зрителем — либо
  вовсе нельзя, и это проще).

## 5. Ошибки ✅

```json
{
  "type": "error",
  "code": "text_not_found",
  "message": "text 8f14e45f-... not found",
  "fatal": true
}
```

`message` — для человека и логов, **не для разбора кодом**. Логика клиента строится только
на `code`. `fatal: true` означает, что сервер закрывает соединение сразу после этого кадра.

| Код | Fatal | Когда |
|---|---|---|
| `bad_frame` | нет | Не JSON, нет `type`, не тот тип поля |
| `unknown_type` | нет | Неизвестный `type` |
| `protocol_version_unsupported` | **да** | `v` из `auth` не поддерживается |
| `auth_invalid` | нет | Токен протух или подпись не сошлась → сессия анонимная |
| `auth_required` | нет | Действие требует аккаунта (гонка, урок) |
| `session_not_started` | нет | `keystroke.batch` до `session.start` |
| `session_already_started` | нет | Повторный `session.start` в живой сессии |
| `session_not_found` | нет | `session.resume` по протухшему `session_id` |
| `text_not_found` | **да** | Python не отдал текст |
| `api_unavailable` | нет | Python недоступен; результат уйдёт из очереди позже |
| `frame_too_large` | **да** | Кадр больше 64 КБ |
| `rate_limited` | нет | Слишком часто (этап 5) |
| `session_timeout` | **да** | Нет нажатий 120 с |
| `room_not_found` | нет | ⚪ этап 4 |
| `room_full` | нет | ⚪ этап 4 |
| `race_already_started` | нет | ⚪ этап 4 |

### Отдельно: невалидные нажатия

Немонотонное время и интервал ниже физиологического минимума — **не повод отбрасывать
нажатие и не повод слать `error`.** Отброшенное нажатие разъезжает состояние сервера и
клиента, и дальше расходится всё: позиция, точность, картинка на экране.

Правильное поведение (и оно же прямо следует из этапа 5 — «помечать, а не блокировать»):
нажатие принимается, забег получает флаг, флаг уезжает в `POST /internal/runs` в поле
`flags[]`, забег не попадает в лидерборды, но виден владельцу.

> ⚠️ Сейчас `messageHandler` при `!res.IsValid` делает `return` — нажатие исчезает молча,
> клиент об этом не узнаёт, и с этого момента `position` на сервере и на клиенте разные.

> ⚠️ Отдельный баг там же: `Validator.ValidateKS` индексирует `sess.Text[sess.Position]` —
> это **байты**, а не руны. На кириллице (2 байта на символ) сравнение поедет с первого же
> символа. В `Session.ProcessKeystroke` рядом всё правильно — через `TextRunes`. Валидатор
> должен ходить туда же.
